# Workout Plan Generator

A single-page Streamlit app that turns a short structured brief about a person into a weekly
workout plan they could actually follow, generated by an LLM through the Groq API.

Built for the AI Engineering Cohort, Session 1 assignment. The interesting part is not the API
call — it's the prompt design and the input model behind it.

---

## What it does

You answer five questions: goal, experience level, days available per week, equipment access,
and time per session. Optionally you add injuries or limitations. Press **Generate Plan** and
you get a markdown plan with:

- one block per training day, each with a warm-up, a table of exercises (sets, reps, rest, cue),
  a cool-down and a realistic total time
- a weekly overview table
- a progression rule for weeks 2–4
- short notes on effort and recovery
- an extra safety section if you reported an injury

## Run it locally

```bash
git clone <your-repo-url>
cd workout-plan-generator

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate

pip install -r requirements.txt

cp .env.example .env             # then paste your key into .env
streamlit run app.py
```

Get a free Groq key at <https://console.groq.com/keys>. Put it in `.env`:

```
GROQ_API_KEY=gsk_...
GROQ_MODEL=openai/gpt-oss-120b
```

`.env` is git-ignored. Do not commit your key.

## How the prompt is designed

This was the actual work. Three decisions did most of the heavy lifting.

**1. Constraints are enumerated, not implied.**
The system prompt lists seven hard constraints — equipment, exact number of days, session
length, injuries, scope, level, no padding — and says explicitly that a constraint may not be
relaxed because the plan would be nicer without it. Vague instruction ("make it appropriate for
their equipment") is what lets a model quietly programme a barbell squat for someone with two
dumbbells.

**2. The output shape is prescribed, not requested.**
Without a skeleton the model writes friendly paragraphs. With one it writes a table:

```
### Day 1 — Lower body
**Warm-up (5 min):** ...
| Exercise | Sets | Reps | Rest | Coaching cue |
**Cool-down (3 min):** ...
**Total time:** about 45 minutes
```

Reps are described in a followable way (reps, seconds for holds, "each side"), and the coaching
cue is capped at 12 words so it stays a cue instead of a paragraph.

**3. Constraints are restated in the user prompt, in the second person of the task.**
The brief repeats `Training days to produce: exactly 3` and `Maximum length of each session: 45
minutes, warm-up and cool-down included`. Models weight the most recent, most specific
instruction. Restating the numbers in the request, right next to the guidance for that
equipment and level, is what stopped the drift I saw in early iterations.

Other deliberate choices:

- **Equipment-specific guidance is injected by lookup**, not left to the model: "No equipment"
  pulls in a paragraph about leverage, tempo, pauses and single-leg variations; "Full gym" pulls
  in a paragraph permitting barbells and cables but not assuming Olympic lifting competence.
- **Level guidance changes volume**, not just adjectives: beginners get 2–3 sets and a
  walk-out-fine instruction; advanced lifters get 4–5.
- **Injuries are framed as exclusions, and "modify as needed" is banned.** Telling a model to
  "suggest modifications" produces the same exercise plus a note. The prompt requires an actual
  safe substitute, stated in one line under that day.
- **Scope is bounded**: no diagnosis, no outcome promises, no supplements, and nutrition limited
  to one sentence about protein and water.
- **The injury addendum is conditional**, so the disclaimer appears exactly when it matters
  rather than on every plan.

### What I changed after testing

Iterating on the prompt was more useful than iterating on the UI. Early versions produced:

| Problem I saw | Fix |
|---|---|
| A plan with 4 days when 3 were requested | Count stated twice, as "exactly N", in both prompts |
| Cable rows for a user with dumbbells only | Equipment paragraph injected by lookup + explicit "never name equipment they do not have" |
| Wall of prose instead of day blocks | Fixed markdown skeleton with a table per day |
| "Do knee-friendly alternatives as needed" | Banned that phrasing; demanded a named substitute |
| Sessions running well past the time budget | Time restated per request and "cut exercises instead of overrunning" |
| Injury plan arrived with **no safety section at all** | The disclaimer text existed but was never wired into the prompt. Fixed: the system prompt now requires a `## Before you start` section, and the request supplies the exact wording |

### Verified with real API calls

Two full generations and one swap, run against Groq (`openai/gpt-oss-120b`):

| Check | Beginner / no equipment / 3 days / bad knees | Intermediate / full gym / 4 days / no injuries |
|---|---|---|
| Day blocks match the request | PASS — 3 | PASS — 4 |
| No unavailable equipment named | PASS — bodyweight, chair and towel only | PASS — barbell, cable and dumbbells, all available |
| Injury safety section | PASS — present | PASS — correctly absent |
| Day headings parseable | PASS — Day 1-3 | PASS — Day 1-4 |

The knee-limited plan avoided jumping and deep knee loading, and used hip-dominant work
instead. The swap feature returned a glute bridge for a bodyweight squat with the reason
"targets glutes/hamstrings similarly to squats while sparing the knees".

## Error handling

Nothing crashes the app. Every failure path ends in a sentence a non-technical user can act on.

| Situation | What the user sees |
|---|---|
| Missing API key | "No Groq API key found. Create a file called .env …" |
| Invalid inputs (e.g. 0 days) | A list of the specific problems, no API call attempted |
| Rejected key | "Groq rejected the API key. Check that GROQ_API_KEY …" |
| Rate limit | "Groq is rate limiting this key right now. Wait about a minute …" |
| Network failure | "Could not reach Groq. Check your internet connection …" |
| Other API error | The status code, plus a suggestion to switch `GROQ_MODEL` |
| Empty response | "The model returned an empty response. Try again …" |
| Response in the wrong shape | "The model replied but not in the plan format we asked for …" |

The shape check (`_looks_like_a_plan`) is intentionally loose: it looks for a "day 1" heading
and a minimum length, because a stricter parser would reject valid plans written with slightly
different heading levels.

## Stretch goals (all implemented)

- **Regenerate** — re-runs with the same constraints. Each press bumps a `variation` counter,
  which nudges temperature from 0.5 up to a ceiling of 0.9, so the exercise selection changes
  without loosening the constraints.
- **Persistence** — plan, profile and variation count live in `st.session_state`, so the plan
  survives widget reruns.
- **Download** — the plan is downloadable as `.md` (keeps the tables) or `.txt` (flattened for
  pasting into notes).
- **Swap one exercise** — pick a day from the dropdown, name the exercise, and get one
  replacement with a reason, generated under the same constraints.
- **Prompt inspector** — an expander shows the exact system and user prompts sent for the
  current profile. Useful for marking, and useful for debugging drift.

## Notes and limits

- This is general fitness guidance, not medical advice, and the app says so. Injury input also
  triggers an explicit "check with a clinician" section in the plan.
- The app deliberately does not write meal plans, calorie targets or supplement advice.
- Model choice is configurable via `GROQ_MODEL`; `llama-3.3-70b-versatile` is the default
  because it follows structural instructions well.
- No key, no plan. The app will tell you rather than fail silently.
